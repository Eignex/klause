# 3.2 Engine projections

The source model of [chapter 3](03-model.md) and the relations of
[section 3.1](03.1-source-relations.md) are never searched directly. Before a solve,
preparation decides which engine owns each variable and factor, and each engine
builds its own projection of the factors it receives. This subchapter describes
that preparation: the execution plan, how factor capabilities are selected, and
how engine state and options stay separate from the source. The
[intended factor retention contract](01-introduction.md#high-level-factors-and-composed-reasoning)
separates variable ownership from concurrent factor mechanisms; the rules below
describe the implemented system.

## Engine projections and factor capabilities

### Binding a source to its execution

`solver.pipeline.SourceAttachment` binds a source to its execution. It retains the
original `Problem` or native source snapshot (polynomial, integer polynomial or
real-function) with its captured semantics. `SourceSetup.prepare` binds the
operation, original objective and direction, finite engine choice, providers and
preparation token; `SourceSetup.execute` dispatches the captured finite or exact
arithmetic operation. A bounded integer/Boolean source with supported native
propagation and no exact-objective preference selects finite ownership before any
arithmetic installation; real coordinates and exact-objective preferences keep
arithmetic preparation. Every file frontend uses the same selection policy. The
plan keeps the original objective while finite engines receive its
minimize-oriented projection. Interrupted preparation publishes no runnable partial
plan, and a heuristic fallback keeps the captured plan rather than preparing an
unrelated model.

### The prepared plan

`Problem.prepareExecutionPlan()` selects immutable ownership and completion data
before search. Shared routing attempts sound open-bound closure before final
nonlinear admission. A relation's captured linear and polynomial encoder support,
together with its available finite completion, selects the arithmetic language; a
factor class alone does not require polynomial traversal.

`PreparedSourcePlan` retains the original source object, canonical execution model,
declaration counts, coordinate mappings, component descriptors and objective
direction. Its sealed payload is finite/linear, polynomial, nonlinear-integer,
transcendental or declined, and consumers dispatch on that variant. `ComponentPlan`
supplies the finite/linear projection, `SharedPolynomialModel` the polynomial
lowering, and nonlinear integer snapshots their own neutral representation (see
[nonlinear integer composition](23-nonlinear-integer.md#solving-and-composition)).
Preparation invents no finite bounds for open integer declarations: variables owned
by an open theory never become finite CP domains, and continuous coordinates are
never integer branch candidates.

`LinearSourceProblem` retains the original rational linear terms, bounds, row
sides, indicator pins and affine objective before any working normalization.
Rational integer objectives use a positive integral scale when representable;
other affine objectives use a private defining column excluded from public counts.
`Problem.componentPlan()` builds a compact remapped CP projection and theory
fragments. Plans belong to the actual source model object, so a rewrite needs a
new plan or the explicit objective-round adapter, which checks that only the
appended bound row changed.

### Opening components

Finite/linear search preparation binds each component descriptor to its canonical
source and opening factory. The registration collection checks source identity and
unique primary factor and coordinate ownership before opening any factory; further
factor participation can overlap those primary paths. Factories retain read-only
source fragments, and every opening creates separate mutable components and an
atom registry.

`PreparedSourcePlan.capabilities` reduces the execution contracts captured on its
components. `admission(strategy, operation)` reports participating arms, procedure
completeness, worker claim authority and explicit unsupported causes. LS and ALNS
offer checked witnesses only. Resource exhaustion belongs to invocation results,
not build-time admission. `withObjective` binds new objective data without
reselecting source ownership.

Built-in factor execution capabilities are declared in
`solver/FactorExecutionCapabilities.kt`, outside `ir`. They distinguish unsupported
routes, deliberate inertness, filtering strength, complete assignment checks,
heuristic scores and sound relaxation families. Capability declarations do not
certify a result or select a source theory. Optional factors store presence
literals: propagation projections read pinned literals conservatively, and
local-search projections read complete assignments. Engine-specific caches, such as table
group no-op caches, MDD transition indexes or local-search occurrence counts, belong
to the projection that built them, keyed by the shared immutable relation arrays.

## Factor projection selection

`FactorProjectionProviders.prepare(problem)` captures immutable selected
propagation, scoring, relaxation and theory encoder descriptors against one
canonical `Problem`. A null descriptor selects an unsupported role, while an
explicit inert descriptor records deliberate absence. The capture applies only to
the identical model; a rewritten or remapped model selects against its own factors.

Encoder selection names the consumer language separately from numerical execution.
Direct and equivalent encoders enforce the whole factor; conditioned encoders
require captured source pins. Relaxation-only and unsupported descriptors confer no
source ownership. Descriptor acceptance is eligibility only: actual installation
and complete-fragment checks still establish which consumer can enforce the source.

Variable ownership is separate from factor participation. `factorOwner` names the
primary enforcing path; `factorEncoded` records additional arithmetic participation,
including factors with propagators. Only relations needed by the arithmetic
component are installed, so one continuous relation cannot promote unrelated finite
factors. Private affine temporaries, Boolean formula names and existential real
coordinates have one acyclic definition in their receiving scope; publication
strips them, and source-coordinate agreement never names them.

`PropagationProblem(problem, selection)` and `LocalSearchProblem(problem, selection,
domains)` open mechanisms from that capture, and `problem.bake(providers)` binds the
selectors to the finite engine projection for one invocation. The neutral `Problem`
has no engine provider field, and coordinate projection keeps source variable ids
out of compact CP storage.

Absent or partial selected deduction does not authorize arbitrary assignments.
Original finite factors are checked at complete points when a built-in complete
check exists; otherwise execution remains unknown. Real completion uses original
source rows independently of any selected relaxation, and published exact
coordinates must satisfy their source relation.

## Search state ownership

Shared search exchanges Boolean literals, semantic integer bounds and typed opaque
theory decisions. Components can maintain private residual state through
`SearchBrancher`, but traversal and decision levels belong to the shared session.
`PropagationSession` remains finite-domain state. Source-keyed `SearchBoolValue`,
`SearchExactIntValue`, `SearchExactRealValue`, `SearchExactAlgebraicRealValue` and
`SearchExactRealExpressionValue`
assignments let each component contribute only the values it owns. Legacy untyped
keys remain compatible. The open pipeline assembles an owned exact coordinate snapshot
against its retained source mapping, preserving arbitrary-width integers, rational,
algebraic and symbolic reals. Missing or multiply represented coordinates withhold
publication. [Typed contributions](30-api.md#typed-contributions-and-migration) define
the decoding and ownership boundary; assembly adds no independent proof authority.

## Public strategy construction

Source strategy factories retain the original Problem and captured schema metadata.
They consume the shared prepared route and arrange its required arithmetic completion
before publishing original-coordinate witnesses. Finite preparation retains that same
PreparedSourcePlan. Exact optimization results remain the existing native result types;
source construction does not issue certificates or normalize proof payloads.
[Library API](30-api.md#source-aware-strategy-entry-points) defines the supported controls
and distinguishes the retained finite facades.

Explicit registered arithmetic collections retain one declared numeric coordinate
owner and guard each participant's contributions against that declaration. Their
agreement participant reads the existing immutable assembly and checks peer source
conditions at those values. See [coordinate agreement](14.4-theory-completion.md#arithmetic-coordinate-agreement)
for admission, incompleteness and proof scope; typed witness decoding remains the
publication mechanism described below.

## Finite execution options

`ExecutionOptions` captures immutable typed settings independently of source models,
workers and invocation allowances. Library callers bind `ExecutionOption` keys to
values directly. Axis settings capture their input lists. Frontends parse remaining
finite `key=value` parameters once after consuming invocation controls. Duplicate
keys retain the last value and the original key ordering for usage diagnostics.
Malformed values retain their diagnostic until the selected route consumes them;
annotation and dry-run rules retain their existing precedence.

Finite requests and planning carry the same captured options. Resolution owns a
fresh consumption view per plan, checks model-dependent catalog and annotation
restrictions, and produces worker factories. Every worker constructs its own mutable
selectors and strategy state; options never contain those instances. Node allowances,
cancellation and lane counts remain invocation arguments, shared or partitioned by
the existing [resource](11-resources.md) and [portfolio](16-portfolio.md) owners.
