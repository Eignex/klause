# 14.1 Traversal and branching

Every pass of the traversal loop starts by choosing what to decide next. This
subchapter describes how branching proposals are collected and ordered, how
component hints choose which side of a split to try first, how arithmetic splits get
stable Boolean names, and how the components that take part in a search are
registered and assembled into one session.

## Lazy branch selection

`SearchBranchProposal` supplies exhaustive, mutually exclusive alternatives without
requiring the deductive component lifecycle. `SearchBrancher` retains its public
component interface for compatibility. Installed and separately supplied legacy
branchers can also implement the proposal interface to declare a category; legacy
branchers without a category participate as finite proposals. Arithmetic built-ins
declare arithmetic proposals. Categories describe the supplying search mechanism,
so a finite heuristic can still propose a Boolean decision.

`SearchBranchSelection.Default` consults the supplied Boolean heuristic first,
then installed components in installation order, then separate legacy branchers,
then independent proposals. `Priority` captures each of Boolean, finite and
arithmetic exactly once and consults them in that order, preserving the relative
proposal order within each category. Reading a category performs no probe. A
selected proposal prevents later probes; null falls through and an empty list
exhausts the residual node.

Each run captures its selection policy separately from Boolean variable selection
and model continuation. Selection changes neither component installation nor
propagation order. The run applies every returned alternative through the same
trail, accounting, cancellation, restart and backjump machinery. Required unknown
checks still prevent exhaustion from becoming a refutation. Invocation scopes and
conditioned traversal floors follow [sessions](10-sessions.md).

A conditioned run retains the decision level at which it opens. Restarts return
to that level, and learned backjumps below it fall back to chronological traversal.
Exhaustion is then conditional. The query owner retracts the condition after the
run; the source root and its immutable atom meanings stay with the session.

For an entirely theory-owned integer difference graph, source-proved relative
interval proposals precede Boolean choices through arithmetic category priority.
They register exact complementary difference predicates in the shared trail; their
obligations belong to [difference logic](19-difference.md). This changes variable
selection without granting a partial potential polarity or witness authority.

## Polarity hints

Once a Boolean variable is selected, a component can suggest which side to try
first. Component-owned candidate hints reach ordinary Boolean traversal through the
`SearchCandidateHints` surface; caller and deferred hints keep precedence. A
preference only reorders the two sides of an already selected split, preserving the
complementary alternative. Propagation and complete component checks keep their
authority, and a hypothetical value supplies no arithmetic fact or feasibility claim.

Built-in providers derive preferences from a completed arithmetic point. A default
opening with a single linear completion owner reuses the point of its last numerical
check for direct comparison preferences; source integers may be fractional there,
so integrality checks and exhaustive integer branching keep their authority. An
opt-in provider (`openHintFlips`) additionally indexes the original source clauses,
optionally recognizes Boolean gate definitions, and prefers the polarity that breaks
fewer clauses under the current point. Index construction and consultations are
bounded, charged to the opening token and discarded on a private limit; see
[native arithmetic allowances](11-resources.md#native-arithmetic-allowances).

Solution-guided LP bounding may read verified peer values before its first local
witness. During that descent, the peer values precede saved phases and numerical
LP value preferences; variable selection and all branch alternatives remain intact.
An admitted local witness ends that ordering priority. LP-free search retains its
first descent before importing solution-guided peers. Importing a hint retains the
trail and learned state and supplies no local incumbent, pruning or publication
authority.

## Source bound atoms

Fractional source integers split at exact floor/ceiling thresholds. CP decisions use
Long values; open theories use arbitrary-precision thresholds. Stable complementary
atoms must exist before first-UIP learning. Boolean atom names belong to one immutable
source root; changing root meaning requires a fresh session. Unnameable conflicts remain
chronological and unexplained.

[SourceBoundAtom](../klause/src/commonMain/kotlin/com/eignex/klause/solver/search/SourceBoundAtom.kt)
owns neutral exact source-coordinate bounds, terms and normalization limits. Integer
splits prove an integral activity and retain arbitrary-precision adjacent thresholds;
rational splits retain complementary strictness. Normalization copies, combines and
orders source terms before registration. Unsupported source kinds, coefficient growth,
term/bit limits and registry capacity decline without installing a partial pair.
Retraction and restart preserve immutable atom meanings and Boolean names. Positive
scalar multiples remain distinct. The linear adapter alone converts these predicates
to LP rows and checks source ids against its source model; retained linear queries
and LP cut-premise naming consume the same neutral predicates. Neither an atom nor
its registration establishes multi-component witness agreement.

The linear component names a source disjunction when arithmetic branching reaches
that group. Only a completely named group enters disjunction propagation. A declined
group retains spent names and leaves the search indeterminate under the same registry
capacity; retraction preserves every registered meaning. Ordinary source rows can
refute their relaxation before disjunction naming. A witness still requires selected
rows for every source disjunction and exact full-source validation.

## Assembly and registration

Source-bound registrations pair prepared execution descriptors with component
factories. The collection validates canonical source identity and rejects duplicate
factor and coordinate ownership before invoking a factory. Standard CP, Boolean and
arithmetic opening uses that collection; the traversal does not select concrete
arithmetic routes. Factories create fresh component instances and retain their
optional branching, model-blocking and conflict-resolution capabilities. Repeated
opening shares read-only source data and completed projections, preserving the
default component and branch order.

`SearchComponentSet` contains mutable participants and permits one session
construction attempt; its claim is consumed before atom attachment, even when
construction fails. Ordinary push/pop and conditioned runs operate within that one
session, and repeated solves open fresh sets from prepared registrations. Prepared
factories receive an opening owner for construction-time resources; the invocation
owns every installed closeable peer, and failure and terminal cleanup follow the
reverse registration contract in [sessions](10-sessions.md#theory-invocation-scopes).

Open linear arithmetic can prepare immutable source row addresses, exact forms and
Boolean dependencies once for one canonical theory fragment through
`prepareExactLiraSource`. Its opaque factory opens a fresh component for each source
session. No opening shares Boolean levels, atom registrations, LP state, reductions
or outcomes with another, and a partial initialization must be closed before a
replacement opens.

Exact affine optimization contexts use the same session and chronological frame
stack. Their authority component records Boolean and integer coverage alongside
checked source bounds or refutations. Resolving one optimized node prunes that node
without issuing a learned clause; only a complete coverage tree can prove a global
optimum or limit, while a checked source ray can finish existentially. See
[linear certification](27-lp-certification.md#refinement-and-strict-inequalities).

Complete assignments use typed source-keyed values from each owner. All required
checks finish before assembly. Missing, unmapped or multiply represented coordinates
leave publication unavailable; decoding supplies neither agreement between peer
fragments nor proof coverage. Published snapshots retain exact values after their
producing components close. [Theory completion](14.4-theory-completion.md) describes
how those values are contributed.
