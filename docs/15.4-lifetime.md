# 15.4 Completion, restarts and ownership

The walk of the previous subchapters moves discrete coordinates and scores them
heuristically. Before anything is published, a candidate needs authoritative values
for its continuous coordinates, and a run that lasts across portfolio slices needs
state that survives suspension without leaking into other operations. This
subchapter covers continuous completion, exact coordinate neighborhoods, restart
anchors, ALNS seeding, and the handles that own a run's state.

## Continuous candidate completion

Finite moves change discrete coordinates; continuous coordinates are completed for
each finite candidate rather than searched. A finite projection uses
`CandidateCompletion` when the source requires arithmetic coordinates, even if its
assignment has no continuous buffer. The completion service checks the pinned
finite candidate against those constraints; a rejected or indeterminate candidate
cannot refute the source model. Completed samples carry authoritative coordinates
and source scope.

When all declarations are continuous, the first candidate requests completion
regardless of its floating score, since an exact rational solution need not have a
zero-violation floating representation. Mixed finite optimization completes
generated starting points that pass the finite checks and compares exact completed
objectives. From a completion-checked incumbent with a continuous objective term, a
pick admits at most two completion probes; a selected finite move and its completed
reals commit as one transition. After a probe charges work, as many further
instructions must accrue before another new query, unless an improving transition
was just accepted. Completion consumes the same move and node allowances.

Numerical completion uses the original-source tolerance callback when the invocation
supplies one; otherwise unavailable exact certification leaves completion
undecided. Exact completion uses bounded point recovery and sparse row repair,
checking every recovered point exactly. Theory-backed linear completion keeps a
worker-private conditioned query owner and charges native work to the containing
ledger. A required polynomial completion can certify finite factors with selected
filtering or inert scoring; the combined polynomial formula must still accept the
unchanged finite point. A completed witness is heuristic incumbent evidence and
supplies no optimum proof.

[Theory contracts](18-theories.md) define the supported graph, linear and polynomial
checks. A propagation-only custom factor receives a private
[full-coordinate finite check](14.2-propagation.md#custom-factor-publication-checks), and an
uncovered continuous constraint declines finite local-search execution.

## Exact coordinate neighborhoods

Models whose coordinates are all decided by an exact theory use a different move
owner. The retained exact-coordinate driver proposes rational coordinate windows and
Boolean pins to a source-bound completion adapter. A coordinate repair relaxes one
pin; compound repairs relax a block, and adaptive neighborhood search weights block
sizes by accepted improvements. Centers, radii, random state, weights and incumbents
survive slices. A rejected repair widens the windows without changing the source
domain or establishing infeasibility.

The linear adapter prepares the source decomposition once and asserts exact rational
bounds and strict objective cutoffs into a private retained theory search. Query
assertions retract after every verdict or interruption, so sibling conditions cannot
inherit a witness, bound or refutation. Generated neighborhoods initialize a private
completion root before preparing a Boolean center; known root values replace the
default false values. Native work and decisions share one allowance across repairs
and also charge the heuristic instruction ledger.

The quadratic adapter uses the same contract with exact algebraic objective ordering,
repairing finite assignments and continuous windows together
([quadratic strategy execution](24-polynomial-real.md#quadratic-strategy-execution)).
Transcendental sources use the same move owner with original-source function
completion ([transcendental real arithmetic](25-transcendental.md)). In every case
only checked completions publish incumbents, and repair refutations or exhausted
windows carry no proof authority.

## Restart anchors

Optimization restart policies receive only accepted feasible incumbents; before the
first one, random restarts diversify the feasibility walk. Anchoring and custom
policies keep the exact best assignment in private packed storage, copying only on a
strict cost improvement and resetting after a published sample. Each consuming
restart receives a fresh expanded sample, so a policy cannot alter the retained
anchor or the live assignment. Fixed-cadence and Luby policies ignore the anchor and
keep no copy. Satisfaction draws, sample streams and resumable satisfaction share
this lifecycle; initialization and the restart right after a publication receive no
anchor.

Built-in anchored perturbations restore exact pins after their random draws and
clear the tabu and configuration epoch while keeping write activity. Restarts wrapped
by definition or implicit initialization record best cost only after reconciliation,
and supplied optimization seeds are reconciled before their first cost observation.

## ALNS incumbent acquisition

ALNS alternates destroying part of an incumbent with repairing it. Adjacency
destruction follows first-discovery breadth-first order through active factor
occurrences, with each variable and factor visited once; disconnected components
keep random reseeding. Repair scopes release both ends of unit Boolean definitions,
including connected aliases. Caller pins are filtered after scope expansion and stay
in the repair assumptions, and interrupted scope expansion is discarded.

Before building its bootstrap, ALNS checks a supplied assignment and the latest
verified shared incumbent, and it polls again between bootstrap slices and before
each neighborhood iteration. A candidate must cover finite and real coordinates,
satisfy the current model and active assumptions, and pass the shared source witness
checker, exactly or under the configured source tolerance. ALNS re-evaluates an
imported point against its own objective and compares strict improvement with that
exact value. Importing an installed point does not publish it again, and samples
transfer no mutable worker state or proof authority.

An absent or unsuitable candidate leaves bootstrap preparation intact, and an
interrupted check leaves the candidate eligible for a later slice. Adoption detaches
and closes both bootstrap handles exactly once before repair opens. When the
bootstrap returns without an incumbent after cancellation, ALNS skips its
local-search fallback rather than seeding again after the deadline. Seed acquisition
renews no allowance; repair uses the original containing budget.

## Handles and exclusive ownership

Local-search optimization handles keep the live assignment, random generator,
factor payloads, restart progress and incumbent between slices. A slice pauses at an
instruction checkpoint or cancellation poll, and an interrupted continuous check keeps
its candidate for the next slice. Moves and restarts count as instructions; the
scheduler charges the observed delta, and the solve-wide move allowance is charged
once across slices. Closing or reseeding discards the retained state. Root
refutations remain authoritative; an unsuccessful walk is incomplete.

An active handle holds exclusive ownership of its solver. Overlapping handle creation
and any other search through that solver, including through another session, throw
`IllegalStateException`. Completion, failure and idempotent close release ownership;
a cancelled slice stays paused and keeps it. The owning session rejects assumption
changes and warm-state reset until release. Portfolio workers use separate solvers
and close a handle before reseeding it.

[LocalSearchEngine](../klause/src/commonMain/kotlin/com/eignex/klause/localsearch/LocalSearchEngine.kt)
owns model preparation, exclusive acquisition, strategies and restart policies. Each
handle owns its cursor, terminal verdict and release through
[LocalSearchRun](../klause/src/commonMain/kotlin/com/eignex/klause/localsearch/LocalSearchRun.kt).
`LocalSearchRunControl` combines lifetime and segment cancellation and keeps the
instruction checkpoint; `LocalSearchProgress` owns residual observations, warm-state
capture and incremental charging. Model projections and immutable indexes can be
shared; mutable run progress cannot.

## Residual diagnostics

Optional residual reporting observes committed assignments at loop and publication
boundaries; probes are never observed. Each strict cost improvement records the
maintained factor degrees summed per factor kind, with reified linear rows split by
operator and input shape, plus up to eight highest-degree representative factors
with bounded samples of their coordinate values, terms and direct definition inputs.
Identifiers refer to the lowered local-search model, not source names. Worker
aggregation keeps one whole observation at the lowest total and never mixes
breakdowns from different assignments. A zero residual establishes neither
completion nor source feasibility, and disabled reporting allocates nothing. The
[CLI](31-cli.md) renders these observations when requested.
